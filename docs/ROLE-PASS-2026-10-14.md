# Four-role pass — 14 October 2026

Manual pass of the web client as each of the four roles, past the landing page.
Run against `main` at 58291b9, local Postgres 16, API on 4000, web on 5173,
machine clock in South Africa (UTC+2). Demonstration accounts from `db/04_seed.sql`.

## Result

Role confidentiality held for every role. Two functional defects were found and
are fixed on `fix/fresh-db-and-dates`; a third is for discussion. Server CI and
Web CI were both failing on `main` at 58291b9 — the first is defect 1, the second
is separate and listed under "Also found".

| Role | Saw | Did not see |
|---|---|---|
| Administrator | margin, ID number, masked bank account, vetting, User accounts, Settings | — |
| Recruiter | consultants, clients, placements | ID number, banking, vetting; `/users` refused |
| Consultant | own placement, own pay rate | bill rate, margin, other consultants |
| Client manager | own company's consultants and bill rates | pay rate, margin, other clients |

Also confirmed:

- Signed out, `/dashboard` shows the sign-in form and no data; `/api/dashboard` and `/api/settings` return 401 without a session.
- Forgot password gives the same answer whether or not the address has an account.
- Rejecting a week needs a reason of at least five characters (400 otherwise, BR-005).
- A consultant cannot approve their own week (403); a week cannot be approved twice (409).

## Defects

### 1. A fresh database is missing the account-token schema and five functions (high) — fixed

`db/migrations-001-approver-lookup.sql` and `db/migrations-002-account-tokens.sql`
say they are included in `01`/`02`, but were not. The README setup and all three
CI workflows apply `01`–`04` only, so on any freshly built database:

- `POST /api/timesheets/:id/submit` returns 500 (Postgres 42883, `placement_approver_user` does not exist) — no consultant can submit a week;
- `POST /api/auth/forgot-password` fails the same way, but the screen still shows its neutral message, so the failure is invisible to the user;
- invitations and password setting have no `account_token` table and no audit actions to record.

The submit failure is what turned Server CI red on `main`. The account suite
(`src/test/accounts.ts`), which would have caught the rest, had no npm script and
never ran in CI.

Fix: the table, type, audit actions, policy, functions and grants are now in
`01_schema.sql` and `02_security.sql`; the migration files stay for databases built
before them and are safe to re-run. `npm run test:accounts` exists and Server CI runs it.

### 2. DATE columns arrive one day early (medium) — fixed

node-postgres turns a `date` into a JavaScript `Date` at local midnight, so on a
UTC+2 server `2026-10-12` is sent as `"2026-10-11T22:00:00.000Z"`. Effects:

- My timesheets matches saved lines with `work_date.slice(0, 10)`, finds none, and shows an empty week after every save or reload. Submitting from that screen then fails with "Record some hours", and saving again would overwrite the stored hours with nothing.
- The approvals list carries `week_start` as `2026-10-11`.
- Invoice line descriptions interpolate the `Date` object (`week of ${t.week_start}` in `invoices.ts`).
- The mobile My week screen and the role-request edit form (`start_date.slice(0, 10)`) do the same day matching and were off by one too.

CI runs in UTC, where the shift is zero. Fix: `pg.types.setTypeParser(1082, (v) => v)`
in `server/src/lib/db.ts`, beside the existing numeric parsers, so a date stays a
`YYYY-MM-DD` string. No server code does arithmetic on a DATE value. Two checks in
`run.ts` — the format of `week_start`, and saved days reading back as the same
days — fail without the parser on a UTC+2 machine and pass with it.

### 3. Every role can read system settings (low)

`GET /api/settings` uses `requireAuth`, so a consultant or client manager can read
company bank details, registration and VAT numbers, and invoice settings. Writing
is admin-only. Not personal data, but more than those roles need. The seeded
`company_bank` value also contains `???`, which looks like an encoding fault in the seed.

## Also found

- Web CI fails on `main`: `Property 'env' does not exist on type 'ImportMeta'`, from the change that hides the demonstration accounts in production builds. The web project needs the Vite client types (`/// <reference types="vite/client" />`).

## Not a defect

The browser agent reported three "critical" findings; after checking:

- "Signed-out access to the dashboard" — the session had not been signed out. Repeated properly, it redirects.
- "Recruiter can open Settings" — true, see defect 3; read-only.
- "Timesheet save does not persist" — it did persist; the display is defect 2.
